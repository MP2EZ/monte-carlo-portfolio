# User Guide

How to run the model, read what it prints, and fix what goes wrong. The [README](../README.md) is the overview; [METHODOLOGY.md](METHODOLOGY.md) is how the model is built.

## First Run

**Easiest path:** open this folder in [Claude Code](https://claude.com/claude-code) and say *"set me up."* It will install dependencies, explain the workflow below, and troubleshoot any errors.

**Manual path** (Python 3.10+):

```bash
pip install -r requirements.txt
```

Then follow the Quarterly Workflow below. The bundled `reference/` data (Ken French / AQR) ships with the repo; the `output/` files are generated by Step 1, so run that first on a fresh clone.

**Want to run it with your *own* tickers?** Open the folder in Claude Code and run
the **`/setup-portfolio`** skill (or just say *"set this up for my portfolio"*). It
drives the whole swap — universe, history sources, sample portfolios — and validates
with `python3 tools/check_consistency.py`. For an incremental one-ticker change, use
**`/add-ticker`**. Procedure details: **[docs/CUSTOMIZING.md](CUSTOMIZING.md)**.

## Quarterly Workflow (Recommended)

### Step 1: Update Market Data (Quarterly)

```bash
python3 data_collection_regime_model.py
```

**What this does:**
- Downloads latest data for all 27 tickers from yfinance
- Integrates Ken French academic data (from 1963 for AVUV, from 1973 for the other factor funds, each until the fund's own or its proxy's history begins)
- Calculates regime parameters (realised volatility per regime, Markov transitions)
- Generates 4 correlation matrices using **15-year rolling window** (baseline + 3 regimes)
  - Window automatically updates: always uses most recent 15 years (180 months)
- **Runtime**: about 10 minutes

**Outputs** (saved to `output/` subdirectory):
- `ticker_parameters_regimes_v8.json` (~70KB) - All 27 ticker parameters
- `correlation_baseline_27.npy` (~6KB) - Baseline 27×27 correlation matrix
- `correlation_low_27.npy` (~6KB) - Low volatility regime correlations
- `correlation_medium_27.npy` (~6KB) - Medium volatility regime correlations
- `correlation_high_27.npy` (~6KB) - High volatility regime correlations

(The pipeline auto-runs the parameter sanity validator at the end.)

### Step 2: Validate

```bash
python3 tools/validate_all.py
```

Structural + data + behavior gate (see [Validation](METHODOLOGY.md#validation)). Must be all-PASS
before a production run. Also run it after any edit to the engine or templates.

### Step 3: Run It

```bash
python3 run.py            # interactive — the normal way
python3 run.py --again    # repeat the last run
python3 run.py --history  # what you have run before
python3 run.py --diff     # compare the two most recent runs
python3 run.py --debug    # ...and report where the wall clock went
```

`run.py` is question-driven: you pick the question and it derives the portfolios.
You never type glide syntax — derisk sets are generated from the tilt family and
bond tiers already in `portfolio_templates.csv`.

**The menu is three questions, named by what changes:**

```
  What do you want to compare?
  > 1  Portfolios                  161 vs 165, or a bond sleeve, on your plan
    2  Retirement choices          retire 60/65/70, claim 62/67/70, savings, withdrawal rule
    3  Market & life assumptions   returns, cash, inflation, lifespan, care costs
    4  Re-run last                 161, 165, 166
    5  Your details                age 37 · $300k · $37.5k/yr · SS $2.5k/mo @70
```

- **Portfolios** holds your plan fixed and compares portfolios, bond sleeves or
  glides: retirement or accumulation-only, which portfolio(s), whether to
  derisk, spending (solve or a fixed amount), policy, paths. A retirement
  comparison then offers to repeat itself under four other return models
  ("IF THE RETURN MODEL IS WRONG"): which strategies are never resolved behind
  the best, the minimax-regret pick, and your plan's success under each.
- **Retirement choices** holds one portfolio fixed and compares plans: each
  option is solved, and read against your current value on the same paths.
- **Market & life assumptions** sweeps what you do not control
  (`tools/sensitivity.py`).

Every prompt has a default, so the common case is a run of presses of enter.

### Your details

Age, plan-to age, retirement age, and your accounts live in
`config/investor.json`, edited from the menu rather than by patching source:

```
  YOUR DETAILS                                    config/investor.json

    1  age                             37
    2  plan to age                     95    horizon 58 years
    3  retirement age                  65
    4  contributions current as of age 36

       account           balance   contribution   growth   until   tax
    5  401k_trad    ⚠    150,000      18,000/yr     2.9%      60   pretax
    6  401k_roth    ⚠     25,000       6,000/yr     2.9%      60   roth
    7  roth_ira           75,000       7,500/yr     4.1%      64   roth
    8  hsa          ⚠     25,000           0/yr     2.9%      60   hsa
    9  taxable            25,000       6,000/yr     3.0%      60   taxable
                      ------------------------------------------
       total             300,000      37,500/yr
       'until' is the LAST age each account contributes.

   10  social security   not set — every run will ask

  Edit which?  [number · a add · x N remove · s save · q cancel]
```

Three things worth knowing:

- **The horizon and your starting balance are derived, not stored.** The plan
  ends at `plan_to_age`, and the balance is the sum of the accounts. Both used
  to be typed separately and both had drifted — `Portfolio Analysis.py` was
  planning to age 87 while `run.py` planned to 95.
- **Row 4 is not your age.** It is when the contribution amounts were last
  trued up, and they compound from it. Changing your age (row 1) prompts to move
  it, because entering current amounts against a stale row 4 gives them growth
  they already contain.
- **⚠ marks a seeded guess, not a fact you gave** — how the 401k splits
  trad/Roth, and the HSA contribution. Harmless to the engine, which sums the
  accounts. Editing an account clears its mark. The `tax` column is shown and set
  in the editor, but the engine ignores it; only `tools/tax_estimate.py` reads it.
- **Rates take `2.9`, `2.9%` or `0.029`** — all 2.9%/yr. A `%` always means
  percent, so `0.5%` is half a percent; a bare number from 1 up is a percentage
  too. Money takes `300000`, `300,000`, `$300k` or `0.5m`.

Nothing is written until you press `s`, and an incoherent record (retiring
before you are born, contributions measured in the future) is refused rather
than saved. These fields reach every run's provenance, so `run.py --diff`
attributes a changed result to a config edit instead of blaming your
strategies.

**Outputs (retirement):** a comparison table, the life-stage spending table
(rank on this one), a robustness block, a confidence note when a row missed its
target, figures in `output/figures/`, and a JSON record in `output/runs/`.

### How many simulations?

**2,000 is right, and 10,000 buys nothing.** Measured
on a 5,000-path reference sample, resampled 400x at each size:

| n | 95% span of the median | 141 vs 140 | 141 vs derisked | 141 vs 145 |
|---|---|---|---|---|
| 250 | 36.7% | 6% | 30% | 96% |
| 500 | 26.4% | 5% | 58% | 100% |
| 1,000 | 19.7% | 6% | 83% | 100% |
| **2,000** | **13.2%** | 10% | **98%** | 100% |
| 4,000 | 9.3% | 11% | 100% | 100% |

The last three columns are the share of runs whose paired CI excludes zero.
2,000 is where the derisking question reaches 98% power — that is the tightest
real question the tool is asked, and it sets the floor.

Two things follow. **The headline median is imprecise at any feasible n**: at
2,000 it is +/-6.6%, error falls as 1/sqrt(n), and +/-1% would need about
87,000 paths. Quote two significant figures, never four. **And 141 vs 140 never
resolves** — 10% at 2,000, 11% at 4,000 — because a gap of about 2% of the median
is below the noise floor. At 2,000, 27% of runs show 140 ahead. That coin flip is real, which is
why `best:` carries a caveat.

Keep the ratio in view: sampling noise is +/-6.6%, while the factor-premium
assumption alone moves lifetime spending 1.6x. Path count is the wrong uncertainty to
optimise.

**Outputs (allocations):** a median-wealth matrix, paired head-to-heads, a
detail table carrying CAGR / volatility / max drawdown / Sortino, the
rebalancing summary, and the five accumulation figures written to
`output/figures/accumulation_*.png`. These last three lived only in the deleted
`Portfolio Analysis.py`, which is why an allocation run used to produce no
charts at all.

**Read the life-stage table, not the headline.** `plan level` is the level the
solver certified at 90% confidence — realised spending runs above it in the
median and below it in bad cases, by margins that differ per policy. What you
actually spend looks like this:

```
  WHAT YOU ACTUALLY SPEND   real $/yr, average within each band
                                    65-74      │    75-84      │    85-94      │  estate
  policy          strategy      median    low  │ median   low  │ median   low  │  median
  guyton_klinger  140             185k   149k  │   306k   161k │   520k   199k │   38.7M
  vpw no reserve  140             437k   172k  │   681k   250k │  1083k   351k │    6.2M
```

`low` is the 10th percentile WITHIN each band, so a row is not one scenario — it
answers "how bad could this stretch be", band by band. A rising policy spends
more later; a flat one does not. This is the comparison a single figure cannot
make, and getting it wrong is what made guyton_klinger look like the winner.

**`--debug`** breaks the run down by phase and recalibrates the estimate:

```
  TIMING   total 6m 38.4s
    guyton_klinger           4m 44.0s ( 71%)
      solve 140                1m 11.1s
        bracketing                   9.6s      3 evals,  1.2k paths
        sampling                    17.7s      6 evals,  2.4k paths
        refining                    19.5s      6 evals,  2.4k paths
        verification                24.3s      2 evals,  3.0k paths
    vpw no reserve              54.3s ( 14%)
      solve 140                   11.8s
        closed form                 11.8s      1 evals,  1.5k paths

    46.5k paths at 8.57ms each
    estimate was 7.0 min, actual 6.6 min — accurate
```

The measured seconds-per-path is written to `config/timing.json` and used for the
next estimate, so it recalibrates instead of drifting. Serial runs (batches under
`solver.PARALLEL_THRESHOLD`) never calibrate — they measure a different execution
mode.

**Sensitivity — do this before trusting any number:**

```bash
python3 tools/sensitivity.py                     # list dimensions + what is known
python3 tools/sensitivity.py premium 1.0,0.5,0.0
python3 tools/sensitivity.py retirement_age 60,65,70
python3 tools/sensitivity.py inflation 0.02,0.03,0.04
python3 tools/sensitivity.py ss_scale 1.0,0.8,0.0
python3 tools/sensitivity.py param_std 1.0,2.0,3.0   # how sure is the model?
```

Use `--sims 800` or more. Below that the dollar answer is poorly conditioned at
low premium, where the success curve is flattest.

It reports whether an assumption moves the **level** (how much you can spend) or
the **ranking** (what you should do), which is the distinction that decides where
effort is worth spending.

Or set the knobs directly for a single run:

```bash
MC_PREMIUM_SCALE=0.5 python3 run.py     # half the historical factor premium
MC_INFLATION=0.04    python3 run.py     # a different inflation assumption
MC_CRISIS_VOL_SCALE=2.0 python3 run.py  # STRESS TEST, not a calibration
```

`premium=0` is not a forecast. It asks what happens if factor premia were a
historical accident. If a conclusion survives it, the conclusion is robust.

## What Automatically Updates

**Every time you run the pipeline:**

✅ **Automatically updated (no manual action needed):**
- All 27 ticker returns (downloads latest from yfinance through current month)
- Historical mean returns (full history, except COST/AVEE use rolling 240 months). These feed `MC_MU_METHOD=historical` and the fallback; under the default `factor` method the engine builds each fund's expected return and band from factor loadings × premia (see [METHODOLOGY.md](METHODOLOGY.md#expected-returns))
- Volatility regimes (labels cut at p30/p70 of each ticker's own 12-month rolling volatility; each regime's volatility is realised over its months)
- Markov transition probabilities (monthly, from full history, conditioned on the market regime)
- Correlation matrices (rolling 15-year window, auto-advances each quarter)
- COST/AVEE history (rolling 20-year window, auto-advances each quarter)

❌ **Never needs updating (static historical data):**
- Ken French CSV files (1963-2025 academic data, already covers full history)
- AQR Quality Excel file (1973-2025 academic data, already covers full history)
- These files provide historical proxies and never need re-downloading

**Bottom line:** Just run `python3 data_collection_regime_model.py` quarterly. Everything updates automatically.

- **AVUV**: about 759 months (1963-07 to current, 2026-10) - longest history

- **VOO**: about 681 months (1970-02 to current)
- **Other tickers**: Varies by inception date (140 months for VUSB to 478 for BND)

- "File not found" → Ken French files missing from `reference/` directory

- History < expected → Check ticker in `ticker_parameters_regimes_v8.json` output

## Updating Market Data

### Update Market Data (Quarterly Recommended)

#### When to Update Parameters

Run `python3 data_collection_regime_model.py` in these situations:
- **Quarterly** (recommended) - Keep parameters current with market conditions
- **After major market events** - Capture significant regime changes (crashes, rallies)
- **Before important analyses** - Ensure latest data for key decisions
- **When script warns** - If `run.py` shows parameters >90 days old

**Time investment**: about 10 minutes (downloads 27 tickers plus proxies, generates all files)

#### The Update Process

```bash
python3 data_collection_regime_model.py
```

**What happens:**
1. **Parse Ken French & AQR data** (7 tickers: AVUV, VTV, AVLV, MTUM, VFMO, JQUA, VBR; plus VOO's 1970s market series)
   - Loads academic portfolio returns from CSV/Excel files
   - Applies weighted blends (e.g., AVUV: 46% ME1 BM4 OP2 + 26% ME1 BM2 OP4 + 28% ME1 BM2 OP3)
   - Applies cost adjustments (expense ratios + implementation drag)

2. **Download yfinance data** (the remaining 20 tickers + proxies for splicing)
   - Downloads actual ETF data from yfinance
   - Downloads proxy funds for middle layer (e.g., DFSVX for AVUV 1993-2019)

3. **Splice historical data**
   - AVUV: Ken French (1963-1993) + DFSVX (1993-2019) + AVUV (2019+) = about 759 months (2026-10)
   - VTV/AVLV/MTUM/VFMO/JQUA/VBR: Ken French (1973+) + proxy where needed + actual = about 645 months
   - Others: yfinance only = 140-478 months

4. **Calculate regime parameters**
   - Historical expected return (arithmetic mean over full history; the default factor method builds returns from loadings instead — see METHODOLOGY)
   - Volatility regimes: labels cut at p30/p70 of a rolling **12-month** volatility, with each regime's volatility taken as the REALISED volatility of the months in that bucket
   - Per-ticker transitions **conditioned on the market regime**, shrunk toward the unconditional row
   - Markov transition probabilities between regimes

5. **Generate correlation matrices**
   - Takes the most recent 15 years (180 months) of spliced returns for all 27 tickers
   - Classifies months into LOW/MED/HIGH regimes
   - Calculates 4 correlation matrices (baseline + 3 regimes)

6. **Output JSON and correlation files**
   - `ticker_parameters_regimes_v8.json` - All 27 ticker parameters
   - `correlation_baseline_27.npy` + 3 regime-specific matrices

**Runtime**: about 10 minutes

All output files are saved to the `output/` subdirectory.

## Portfolio Templates

Portfolios live in `portfolios/portfolio_templates.csv`, organized by a numbering system.
The file holds only **1xx rows, all 100% equity**; the tens digit is the factor tilt.

**Bond tiers are not stored as rows.** They are synthesised from a row's own
equity sleeve by `loaders.with_bonds` and written in a run as `141+10` (141 with
10% bonds), optionally with a bond mix (`141+10:bnd_only`), so only the bond
weight differs from the control. The `design-runs` skill documents the syntax.

**Tens digit = factor tilt** (within each hundred):
- **x0x**: core / no tilt
- **x2x**: value tilt
- **x4x**: momentum tilt
- **x5x**: momentum + international-mix experiments (Simple Intl, EM weightings, VEA/VWO)
- **x6x**: momentum + value
- **x7x**: momentum + value, continued (x6x is full; 170 = 168 without COST)
- **x8x**: quality tilt

The ones digit is the variant within a tilt. Key handles: **140** = the base
the library's comparisons start from, **141** = your holdings: the row
`tools/update_holdings.py` overwrites with your own allocation (it ships holding
the author's, as an example).

**Starters** — plain portfolios with no single stock, to compare your own against:
- **102** = **VT one-fund benchmark** — "just own the world"
- **103** = **three-fund index**: VTI 70% / VXUS 30%
- **122** = **Avantis factor tilt**: VOO with 15% small value (AVUV) and 15% large value (AVLV), Avantis international

The rest of the library is one family built around the author's portfolio —
140 and its variants — kept because [RESULTS.md](RESULTS.md) was measured on it.

**Comparison rows:**
- **145** (momentum) = **Vanguard-only mirror** of the base, mapping every sleeve to a Vanguard fund (AVUV→VBR, etc.) for an all-Vanguard comparison

**Decoding the `name` column** (e.g. `70D:30I // 100:0 // 5C // 12AVUV // 12VFMO`):
- `70D:30I` — 70% domestic (US) / 30% international equity
- `100:0` — equity : bond split (always 100:0 in the stored rows)
- `5C` — 5% COST (single stock)
- `12AVUV` — 12% AVUV (US small value)
- trailing fund codes (e.g. `12VFMO`, `9.5VTV`) — factor overlays and their weights

**Example**: `140` = 70% US / 30% intl, 100% equity, 5% COST, 12% AVUV, 12% VFMO (the base)

> The derived columns (`bond_pct`, `us_pct`, `tilt_family`, …) are computed from the
> allocations by `tools/annotate_templates.py`, and section headers by
> `tools/add_section_headers.py` — re-run both after bulk edits.

## Retirement Scoring (what the numbers mean)

### The four policies

| policy | who absorbs a bad market | character |
|---|---|---|
| `constant_real` | the portfolio | same amount every year; the ONLY one that can deplete |
| `guyton_klinger` | shared | cuts 10% when the withdrawal rate drifts 20% above its starting rate; raises it when the rate drifts below (how fast: see below) |
| `vpw` | you | amortises the balance to age 100 (or five years past the plan-to age, if later), so the rate RISES with age; spends down deliberately |
| `fixed_pct` | you | fixed % of balance; a 35% crash is a 35% pay cut |

Two **sourcing** rules decide which holdings fund a withdrawal. `pro_rata` sells
every holding proportionally and leaves weights untouched. `excess` (the default)
sells from what is above target, so it rebalances as it withdraws — which is why
CAGR and Sortino differ very slightly across policies under `excess` and are
identical under `pro_rata`.

**`guyton_klinger` has three response speeds** (`policies.GK_RESPONSE`), `slow`,
`medium` and `fast`, default `fast`. The downside pair is identical in all
three: when the withdrawal rate rises past 1.20x its starting rate, spending is
cut 10%. They differ in how quickly spending follows a growing portfolio, by
raising it when the rate falls below a floor:

| response | rate below | raise |
|---|---|---|
| `slow` (the original rule) | 0.80x | +10% |
| `medium` | 0.90x | +15% |
| `fast` (default) | 0.95x | +20% |

A faster ratchet raises spending after a good year and must then cut after a
bad one. The per-year cut stays capped at 10%, but consecutive cuts are
possible, so read `worst yr` and the life-stage `low` column before changing it.

**`vpw` amortises to age 100, or to five years past the plan-to age if that is
later, not to the horizon.** Amortising to the horizon
would demand a ~100% withdrawal at 94, an artefact of a fixed endpoint rather
than a policy anyone would follow. So `vpw` normally leaves a balance at 95 even
with no reserve. A **reserve** is held back from the amortisation on top of that:
it is a dial that trades spending for estate, not a target for the end balance.
Read the `bequest` column for what actually lands.

### Plan level vs what you spend

`plan level` is the largest annual figure the solver can certify at 90%
confidence. It is **not** a forecast:

- realised spending runs **above** it in the median and **below** it in bad cases
- the margin differs per policy — p10 of the first band over the plan level ran
  100% for `constant_real`, 86% `guyton_klinger`, 67% `vpw`, 47% `vpw+5M`

A number meaning "roughly what you get" for one policy and "maybe half of it" for
another cannot rank them. **Rank on the life-stage table.**

### Adequacy: the worst 10-year window, not lifetime

A path succeeds if it never ran out AND **every rolling 10-year** average of
spending cleared the floor (85% of plan by default). A retirement under 10
years is scored as one window. Until 2026-10-21 the rule was THIRDS of the
retirement span (`config['adequacy'] = 'thirds'` replays it): a third of a
35-year retirement is a 12-year band and of a 25-year one an 8-year band, so
the test was more lenient the longer you planned or the earlier you retired —
165 certified $123.0k planning to 100 and $120.05k to 95 on paths identical
for their first 30 years. A window has one length everywhere, and a longer
plan has every window a shorter one has, so it never certifies more.

The lifetime mean was shape-blind: a bad first decade could be repaid by a rich
ninth. The share of *passing* paths that ran short in the first band was 0.0%
`constant_real`, 3.8% `guyton_klinger`, 8.5% `vpw`, 12.5% `vpw+5M` — monotone in
how back-loaded the policy is, so the criterion was lenient exactly where it
should have been strict.

The thirds cost 28–30% of the headline for the variable policies and **58%** for
`vpw+5M`, and left `constant_real` exactly unchanged — it spends the target
every year, so every band equals the lifetime mean; the window costs a further
7.3% on 165 at 65–95 ($120,050 → $111,334). It is not a "your sixties" test: the binding stretch differs by
policy, and `--debug` reports where it starts. `vpw`'s weakest stretch is early (its
rate rises with age); `guyton_klinger`'s is late (p10 spending declines across
the bands). Set `config['adequacy'] = 'lifetime'` for the old behaviour.

### How the solver finds the level

Two routes, chosen by whether the policy consumes the target.

**Closed form**, for `vpw`: its withdrawals are a function of the balance alone,
so the paths do not move when the target does — verified bit-identical at a $200k
and a $450k bar. Success is then `P(statistic ≥ floor × spend)` and the answer is
a quantile, not a search. Exact, and 14x faster.

**Estimated crossing**, otherwise: sample the bracket, pool adjacent violators to
impose the monotonicity we know holds, fit the neighbourhood of the crossing, then
move the level onto the **verification** sample with one Newton step. On a
deterministic universe the curve is a step rather than a slope, and the straddling
pair is bisected instead — a line fitted through a step is biased, not merely
imprecise.

Both routes set the level on the verification sample deliberately. The search
sample is a subset of it (both seed `42 + sim_id`), so whichever way that subset
leans it leans the same way at every spend — worth **17%** on `guyton_klinger`
under the old bisection. `--debug` prints the correction per solve:

```
    crossing  $140,526 (fitted, on the search sample)
    verified  $163,000 (+16.0% onto the verification curve, 90.1%)
```

A solved level is estimated from a finite sample, so it lands *near* 90% rather
than on it. The run prints what each row actually achieved when it differs by
more than a point.

## Performance Expectations

### Data Collection Pipeline
**Typical Runtime**: about 10 minutes, most of it network downloads.

### Monte Carlo Analysis
**Runtime** scales with paths × strategies × years. `run.py --dry-run` prints
an estimate before anything runs: two strategies solved at 3,000 verification
paths (twice the 1,500 default), planned to 95, estimate about 7 minutes.

**Memory** scales with paths per strategy, since each worker holds its paths'
monthly balances until they are reduced to percentiles.

**Output File Sizes** (in `output/`, gitignored):
- `ticker_parameters_regimes_v8.json`: ~70KB
- Correlation matrices (.npy): ~6KB each (4 files)

`run.py` writes a small JSON record per run to `output/runs/` (scalars and
percentiles only — a few KB) and figures to `output/figures/`. Path arrays are
~48MB per portfolio and are deliberately **not** persisted; percentiles answer
every question a stored run gets asked. Use `run.py --history` and `run.py --diff`
to compare runs across a quarterly regen.

## Troubleshooting

### ERROR: Parameter file not found

**Problem**: `ticker_parameters_regimes_v8.json` missing from working directory

**Solution**: Generate the parameter file:
```bash
python3 data_collection_regime_model.py
```
**Time**: about 10 minutes. Creates all necessary JSON and .npy files.

---

### WARNING: Parameters are X days old

**Problem**: Parameter file exists but hasn't been updated recently

**Context**: `montecarlo/loaders.py` checks the `last_updated` timestamp in the JSON file and warns if >90 days old. Markets change, so quarterly updates recommended.

**Solution**: Update parameters if needed:
```bash
python3 data_collection_regime_model.py  # Takes about 10 minutes
```

**When to ignore**: If you're deliberately using historical parameters for backtesting or comparison.

---

### ERROR: Correlation file not found

**Problem**: Correlation matrices missing or misnamed

**Solution**:
1. Check what correlation files exist:
   ```bash
   ls output/correlation_*.npy
   # Should see: correlation_baseline_27.npy, correlation_low_27.npy,
   #             correlation_medium_27.npy, correlation_high_27.npy
   ```

2. If missing, regenerate:
   ```bash
   python3 data_collection_regime_model.py  # Generates all correlation matrices
   ```

3. If files exist but named differently, update the `correlation_files` metadata in the JSON to match actual filenames.

---

### ERROR: Ticker list mismatch

**Problem**: a run raises a ticker-list mismatch at startup.

**Root cause**: the JSON parameter file was generated from a different ticker set than the current `loaders.MODEL_TICKERS`.

**Solution**: the ticker universe lives in ONE place — `MODEL_TICKERS` in `montecarlo/loaders.py` (`data_collection_regime_model.py` imports it via `from loaders import MODEL_TICKERS as TICKERS`). So:
1. Confirm `MODEL_TICKERS` in `montecarlo/loaders.py` is what you want.
2. Regenerate parameters: `python3 data_collection_regime_model.py`
3. Verify everything agrees: `python3 tools/check_consistency.py` (must be all-PASS)

**Note**: To add/remove tickers, edit `MODEL_TICKERS` and follow `docs/RUNBOOK_tickers.md` (or run the `/add-ticker` skill).

### Allocation doesn't sum to 1.0

**Problem**: Portfolio allocations don't sum exactly to 1.0

**Solution**: Each portfolio row in `portfolio_templates.csv` must have ticker
weights summing to ~1.0 — the loader rejects any row outside `0.99–1.01` and names
the offending portfolio. Fix that row's weights (the derived nav columns are ignored
by the sum check), then re-run `python3 tools/check_consistency.py`.

---

### Out of memory errors

**Problem**: Script crashes with memory error during multiprocessing

**Solution**: use fewer paths. Pass `--sims N` with `--spec` (paths per strategy;
the search stage gets N/2), or set `sims` (or `verify_sims` / `search_sims` for a
solved run) in the spec. The worker pool always uses every core
(`cpu_count()`), and there is no setting to limit it.

---

### Very slow performance

**Problem**: Script runs much slower than expected

**Check**: CPU usage should show all cores at 100% during simulation

**Solutions**:
1. Verify multiprocessing is working (check Task Manager / Activity Monitor)
2. Reduce number of cores if thermal throttling occurs
3. Close other applications to free resources
4. Run on a machine with more cores

**Expected performance**:
- 10K simulations, 8 cores: ~5-8 minutes
- 10K simulations, 4 cores: ~10-15 minutes

### Advanced: If parameter loading fails

The embedded backup parameters that used to live in `Portfolio Analysis.py` were
**deleted** (v3.2). They had gone stale by five tickers — a 20-ticker snapshot
against a 25-ticker universe — so following the old "revert to embedded" advice
would have silently produced a wrong model. Being inside a string literal, they
were invisible to `tools/check_consistency.py`.

If loading fails, fix the cause rather than bypassing it:

1. `python3 tools/validate_all.py` — says which stage and which ticker
2. Missing/corrupt `output/` files → re-run `data_collection_regime_model.py`
3. Ticker mismatch → the universe lives once in `loaders.MODEL_TICKERS`; see
   [docs/RUNBOOK_tickers.md](RUNBOOK_tickers.md)
4. `output/` is gitignored, so git holds no earlier parameter set. Back `output/` up before a regen (the `refresh-parameters` skill does, into `output/backups/`) if you may want to go back
